# 微服务中的内容发布链路：服务边界、互动统计与搜索同步

内容发布场景可以用来分析微服务之间的调用与数据流。以下是通用架构示例，不依赖特定产品或业务系统：入口服务负责路由，身份服务验证用户，内容服务管理正文与分类，互动服务记录评论和收藏，搜索服务维护查询索引。

## 服务调用与身份边界

```text
客户端 -> Gateway -> 内容 API -> 内容服务 -> MySQL
                         |-> 身份校验
                         |-> 互动数据
                         `-> 搜索索引更新
```

网关负责入口路由、跨请求过滤和统一观测，不应代替业务服务完成资源级授权。服务间使用 OpenFeign 等 HTTP 客户端时，要定义连接与读取超时、错误映射及重试策略。写请求不能因为网络失败就无条件重试；调用方需要幂等键或可判定的业务结果。

令牌只应携带必要的身份声明。下游服务应根据自身信任边界校验身份与资源权限，避免仅凭前端传来的用户 ID 进行授权。验证码和短期登录状态可有过期时间，但不能在日志、指标标签或 Redis 键中暴露原始手机号等个人信息。

## 内容与互动数据

内容元数据、正文、评论和用户关系具有不同的查询与生命周期。正文可以与元数据分离存储；评论按内容 ID 分页查询；用户收藏关系可用关系表或 Redis Set 等结构表达，具体选择取决于是否要求持久化、事务和按用户反查。

阅读、点赞等高频计数可以先在 Redis 中聚合，再周期性写回关系数据库。但累计更新需要处理并发、重复事件、任务重试与进程崩溃。覆盖写入可能丢失后续增量；增量合并则需要唯一批次或版本来避免重复累加。Redis 只保存易失统计时，要明确重启和数据过期后的恢复策略。

## 搜索索引同步

搜索索引是内容数据的派生读模型。直接在数据库事务中同时写 MySQL 与 Elasticsearch 存在部分成功窗口；可以通过 Outbox 或变更日志异步传播变更，再由消费者幂等更新索引。

```text
MySQL 事务提交 -> 变更事件 -> RabbitMQ -> 索引消费者 -> Elasticsearch
```

消息需要区分发布确认与消费确认。重复投递由内容 ID 和版本号吸收；删除事件要有墓碑或明确的删除同步策略；消费失败需要重试上限与死信处理。查询结果返回前仍应通过权威数据校验可见范围。索引延迟意味着最终一致，而不是强一致。

## 排序与周期任务

定期计算的排行榜是某个时间点的快照，和 Redis Sorted Set 上的实时排序不是同一种语义。快照要记录计算窗口、版本和生成时间；任务重跑应可覆盖同一批次结果，避免重复计数。对于单实例定时器，多实例部署时还要处理重复触发、任务租约和失败恢复；Quartz 或分布式调度器能协调触发，但不能自动保证业务操作幂等。

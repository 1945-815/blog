# 数据库事务、索引与重复提交问题

## 问题背景

提交按钮可能被重复点击，客户端也可能在超时后重试。同一个业务动作因此到达服务端多次。仅在页面禁用按钮不能保证后端只写入一条记录。

## 核心原理

事务保证一组数据库操作的原子性和隔离语义；索引支撑查找并影响写入成本；唯一约束由数据库在并发下最终裁决重复键。幂等策略可以结合业务唯一键、幂等令牌和状态转换设计。

## 实现示例

例如预约可设计 (user_id, slot_id) 唯一键；服务层先做友好校验，再执行写入，捕获重复键并映射为稳定业务结果。多表更新放在清晰的事务边界内。可用两个并发请求验证只有一个成功创建。

并发请求都可能先读到“不存在”，随后尝试插入。数据库唯一索引负责串行化冲突并让一个写入失败。事务回滚其本地变更，但不会自动撤销已经发送的外部消息或 HTTP 调用；跨资源一致性需要额外设计。

### 源码与机制观察

**源码与数据库观察：**检查 InnoDB 唯一索引冲突、事务隔离和锁等待行为；可用两个连接并发插入同一业务键验证数据库约束。Spring 声明式事务还需关注代理调用、自调用和异常回滚规则。

```sql
ALTER TABLE appointment
  ADD CONSTRAINT uk_user_slot UNIQUE (user_id, slot_id);
```

## 应用场景与边界

通过合成的预约表建立唯一约束，再让两个请求尝试插入相同业务键，可以观察数据库如何处理竞争并拒绝重复写入。验证时应同时检查唯一键冲突和受影响行数。

## 边界与常见问题

先查后写不是并发安全保证；事务也不能替代唯一约束。唯一键应包含真正业务身份，错误码要区分重复预约与系统异常。避免将外部网络请求放在长事务里。

## 改进思路

用业务唯一键兜底并发重复写入，服务层把冲突转换为稳定响应；再结合查询条件和执行计划检查索引是否真正被使用。

## 设计取舍与结论

事务、唯一约束和业务幂等各有职责。并发正确性要通过数据库约束和真实并发验证，而非依赖前端交互。

# 评论或举报审批如何接入 Activiti 流程

## 问题背景

内容管理系统可能需要处理举报、审核和反馈。流程引擎适合承载可配置的审批步骤，但举报记录、审核结论和处置动作仍属于业务域。

## 核心原理

提交举报先保存业务记录和唯一业务键，再启动关联流程；审批人完成任务后，服务层验证意见和记录状态，更新业务结论并保留审计。流程实例 id 应作为关联信息，不应替代举报 id。

## 实现示例

接口可拆为创建审核请求、查询本人记录、查询待办、提交处理意见。重复提交用业务约束处理；处理结果包括通过、驳回等明确枚举。响应只返回当前用户可访问字段，审计记录包含操作者和发生时间。

审核请求经过校验与持久化，再发起流程实例；任务路由依据流程定义和变量创建待办。处理提交先校验任务归属和业务当前状态，再完成任务并更新业务记录。跨系统失败要能发现并补偿。

### 最小审计字段

审核请求应能回答提交人、对象、原因、创建时间和当前处理结论；处理记录应能回答操作人、处理动作、意见、任务标识和发生时间。对流程定义升级、任务转办或重复回调，要预先确定旧实例如何继续运行。可以先用一条合成审核请求验证“提交—待办—通过/驳回”闭环，再检查权限和失败重试路径。

**示例代码或流程：**

```text
审核请求 -> 创建流程实例 -> 审批待办
处理动作 -> 校验办理人和当前状态 -> 完成任务 -> 写入业务结论
```

## 应用场景与边界

该示例展示内容审核请求与流程实例的关联，审核意见和处理人均为合成数据。

## 边界与常见问题

不要接受客户端传来的任意审批人作为可信数据；不要允许已结束流程再次完成。流程回调与业务状态更新要考虑事务边界、重复请求和审计一致性。

## 改进思路

校验当前任务办理人和业务状态，保留操作审计；流程完成与业务结论发生偏差时能够对账。

## 设计取舍与结论

工作流让审批路线更易表达，但业务记录、权限和最终处置必须由应用明确掌控。

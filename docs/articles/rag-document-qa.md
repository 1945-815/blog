# RAG 文档问答的基本链路：文档、检索与模型 API

<div class="meta-line"><span class="status-tag practice">应用集成</span><span>架构草稿 · 不代表模型训练经历</span></div>

RAG（检索增强生成）把“找资料”和“组织回答”拆成两步：先从自己的文档集合中找到与问题相关的片段，再把片段作为上下文交给模型生成回答。对于企业文档问答，检索结果的相关性和来源可追溯性同样重要。

## 一次问答通常经过哪些步骤

```text
文档导入 → 文本抽取 → 分段 → 生成向量并写入索引
用户问题 → 问题向量化 → 检索相关片段 → 组装上下文
         → 调用模型 API → 返回回答与引用来源
```

简历描述的实践包含 Elasticsearch 搜索数据同步、向量检索和模型 API 接入。本文只按应用链路说明这些组件如何衔接，不把它描述为训练或微调基础模型。

## 文档导入与索引

导入阶段需要保留可用于过滤和引用的元信息，例如文档标识、标题、分类、片段编号和来源路径。文本切分应保留足够上下文，避免把表格、标题或段落边界拆散。

对每段文本生成向量后，将向量与文本及元信息一起写入支持检索的存储。具体的向量维度、索引参数和过滤条件应与所选模型及存储配置一致，不能照抄其他项目的固定值。

## 查询与回答

查询阶段可以先把问题转换成向量，再按相似度召回候选片段。若系统还需要关键词检索，可将关键词匹配和向量召回结合，再按业务规则过滤或重排结果。

交给模型的提示内容至少应说明：只依据给定上下文回答；上下文没有答案时明确说明；保留或返回所用片段的来源标识。具体实现还需要限制上下文长度，并处理检索为空、模型超时和返回格式异常等情况。

## 排查时拆开看

回答不准确时，可以先分别检查检索和生成：

1. 输入文档是否成功解析并进入索引？
2. 查询是否召回了与问题相关的片段？
3. 召回片段是否包含足够上下文？
4. 提示内容是否把问题和片段清楚传给模型？
5. 回答是否包含可核对的引用来源？

拆开排查可以避免把所有问题都归因于模型，也避免因为模型生成流畅就误认为检索正确。

## 小结

RAG 应用的核心链路是文档处理、检索、上下文组织和模型调用。能把每一段的数据输入、输出和失败路径讲清楚，就足以展示应用工程能力；无需把应用集成包装成模型训练。

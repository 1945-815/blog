# RAG 文档问答的基本链路：文档、检索与模型 API

### 文章定位

本文基于路线图主题展开。实习项目相关叙述严格限定在简历已列出的职责；无法确认的工程细节使用通用示例说明，不冒充生产实现。

### 学习目标

- 理解业务问题与技术组件的对应关系。
- 能画出关键模块或状态流转，并解释失败边界。
- 能区分团队成果、本人负责内容与个人练习。

## 一、为什么学习这个技术

只把问题交给大语言模型时，模型可能缺少私有或最新资料。RAG 在生成前检索外部知识，并把相关片段作为上下文，适合需要关联文档来源的应用探索。

## 二、技术原理

典型链路包含文件解析、文本清洗与切分、Embedding、向量或混合检索、候选重排、上下文组装、模型生成和引用回传。检索负责找材料，模型负责基于上下文组织回答；两者应分别评估。

## 三、核心代码实现

用公开文本建立小型知识集，为每个片段保留文档 id、标题、页码或段落等元信息。问题进入检索后取回少量候选，构造包含来源的提示词，再调用模型 API。若证据不足，应允许系统说明未检索到依据，而不是强行回答。

离线阶段产生向量并写入存储；在线阶段把查询转换为向量，检索相关片段，组装 prompt，再调用生成 API。切分策略、Embedding 模型、召回数量、上下文窗口和模型版本都会影响结果。应用集成并不等于训练模型。

### 源码与机制观察

沿数据流分别保存解析文本、候选片段、最终上下文和模型响应元数据。排查错误时先检查检索是否命中正确材料，再判断上下文是否完整，最后检查生成是否忠实引用证据。

## 四、真实项目落地

简历涉及文档问答集成。本文用公开或自造文档说明解析、检索、上下文组装和模型 API 调用，区分团队协作与独立 Demo。

## 五、遇到的问题

不要把模型回答当成事实；不得把用户文档或密钥发送给未获授权的第三方模型。引用要能映射回来源。请求超时、空召回、模型限流和内容权限过滤都需要单独设计。

```text
用户问题 -> query embedding -> 检索候选片段
            -> 权限过滤与上下文组装
            -> 模型 API -> 答案 + 来源引用
```

## 六、优化方案

分别观察检索候选、最终上下文和生成回答；证据不足时允许明确回答未知，并保留来源引用。

## 七、个人思考

RAG 的关键是可观察的数据链路和可信来源管理。它改善知识接入方式，但不能保证模型永远正确。

## 延伸：面试问答

### RAG 和微调的区别？

RAG 在推理时检索外部资料并提供上下文；微调调整模型参数，适用目标和数据治理方式不同。

### 回答错了先排查哪里？

先检查召回片段是否相关、权限是否正确，再检查上下文组装和生成环节。

### 为什么要返回引用？

引用支持用户核验依据，也帮助区分系统使用了哪些文档；必须保留稳定来源元数据。

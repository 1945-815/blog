# 用 Docker 搭建本地后端开发环境

### 文章定位

这篇文章对应路线图中的 开发环境 主题，文章使用可复现的技术链路解释问题；涉及实习内容时只描述简历能够支撑的职责，不补充未确认的实现细节或效果数据。

### 学习目标

- 理解关键组件的职责与边界。
- 能搭建或追踪最小流程，验证正常和失败路径。
- 能把 Demo 结论与实际项目经验分开表达。

## 一、为什么学习这个技术

多人协作时，本地依赖服务的版本和启动方式容易不一致。Docker 能让服务以容器形式运行，但它不会自动解决数据备份、安全和生产部署问题。

## 二、技术原理

镜像提供可复用文件系统和启动配置，容器是镜像运行实例；端口映射连接宿主机与容器，数据卷让数据生命周期独立于容器。Docker Compose 用配置描述多个相关服务。

## 三、核心代码实现

选定 MySQL、Redis 等本地依赖的明确镜像版本；只开放必要端口，使用本机开发口令并将数据放进命名卷。README 写出启动、查看日志、停止和清理命令；删除卷会丢本地数据，需说明影响。

```yaml
services:
  redis:
    image: redis:7
    ports:
      - "6379:6379"
    volumes:
      - redis-data:/data
volumes:
  redis-data:
```

### 与本地 Docker 课程资料的对应

`09.Docker/09.Docker/` 的课堂笔记记录了一条手动发布 Vue 静态站的学习流程：启动 CentOS 容器、安装 Nginx、将构建产物 `dist` 放到 Nginx 文档目录、以前台方式运行 Nginx，再练习 `docker commit`、镜像 `tag`、推送私有仓库，以及在另一台机器 `pull` 后运行。笔记还记录了 CentOS 8 软件源变更造成的安装问题。这些是课程操作过程，不是我独立搭建或维护的发布环境。

手动进入容器修改文件再 `commit` 有助于理解镜像与容器，但步骤容易遗漏，也不方便代码审查和重复构建。项目交付更适合把 Nginx 配置、静态资源复制和启动命令写入 Dockerfile，再通过镜像仓库发布；Spring Boot 镜像的构建例子见 [Spring Boot 多阶段镜像](/articles/059-springboot-docker-multistage)。复制目录后要检查 `index.html` 实际落在 Nginx 的文档根目录，避免多出一层 `dist/` 目录。

本地 `10.9 Docker基础操作与部署` 笔记也覆盖镜像、容器、端口映射和网络排查。容器 IP 是运行时分配值，容器重建后可能变化；同一 Compose 网络内的应用应优先通过服务名访问依赖，不要把课堂看到的某个 bridge IP 写成固定地址。

### 源码与机制观察

检查 Dockerfile 的基础镜像、层缓存、工作目录和启动命令；检查 Compose 中服务、端口、卷和环境变量映射。使用 docker inspect、logs 和 ps 验证实际状态。

Compose 根据 YAML 创建网络、卷和容器，再按依赖关系启动服务。应用连接地址要区分宿主机和容器网络内的服务名。健康检查可以表达就绪条件，但应用自身仍需处理依赖启动延迟。

## 四、真实项目落地

在个人电脑上用容器启动数据库或 Redis，再用示例应用连接它们；镜像版本、端口和卷写入 README 便于复现。

## 五、遇到的问题

不要使用浮动 latest 作为长期复现版本；不要把密钥写进公开仓库。容器启动不代表数据库已可接受请求。不要把生产数据复制到本地 Demo，清理命令前确认是否会删除卷。

## 六、优化方案

固定镜像版本、缩小端口暴露、声明数据卷和就绪检查；本地配置和正式环境分别管理。

## 七、个人思考

Docker 适合把本地依赖的启动步骤写清楚。复现性来自版本、配置和数据生命周期共同明确，而不是单纯“容器化”。

## 延伸：面试问答

### 镜像和容器的关系？

镜像是创建运行环境的模板，容器是镜像启动后的隔离实例。

### 容器删除后数据会留吗？

容器自身可写层会随容器删除；挂载到持久卷的数据通常独立存在，除非显式删除卷。

### 本地 Compose 文件可以直接用于生产吗？

通常还需生产级密钥管理、网络边界、监控、持久化、备份和资源配置，不能直接照搬。

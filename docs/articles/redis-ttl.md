# Redis TTL 与缓存边界：从临时状态到热点数据

<div class="meta-line"><span class="status-tag">文章草稿</span><span>Redis 实践 · 示例代码需按项目客户端适配</span></div>

Redis 的过期时间常用于两类不同需求：验证码、临时状态这类“到期后就不再有效”的数据，以及数据库旁的热点缓存。两者都可能设置 TTL，但删除规则、失效后怎么办，完全不同。

## 临时状态：到期就是业务规则

验证码通常需要同时考虑键命名、使用场景、有效期和重发策略。一个简化的 Redis 命令示意：

```text
SET verify:login:session-123 483921 EX 300 NX
```

这里设置了 300 秒有效期，并尝试只在键不存在时写入。真实实现还需要考虑：验证码是否一次性使用、错误次数如何限制、重发是否更新旧值、日志是否会记录敏感内容。密钥、令牌和验证码不应出现在公开仓库或普通业务日志中。

如果数据具有“过期后不应继续使用”的含义，过期不是缓存优化，而是数据规则的一部分。读取时也要把键不存在作为正常情况处理。

## 热点数据：缓存是可丢弃副本

常见缓存旁路流程是：先查缓存，未命中时查数据库，再回填缓存。缓存内容应该可以从权威数据源恢复。

```text
read(key):
  value = redis.get(key)
  if value exists:
    return value

  value = database.query(key)
  if value exists:
    redis.set(key, value, ttl)
  return value
```

这个流程简洁，但还需要回答缓存空值怎么处理、数据库更新后如何删除或刷新缓存、并发未命中会不会造成重复查询、反序列化失败如何兜底等问题。

## TTL 不是一致性方案

较短 TTL 可以限制旧缓存存活时间，但不会保证数据库和缓存实时一致。更新数据时常见的做法是先更新数据库，再删除缓存；如果删除失败，需要有重试或后续校验思路。具体顺序还要结合业务读写并发讨论，不能把一种写法套到所有场景。

对大量同一时间写入的缓存，可以在 TTL 上加入少量随机抖动，减少集中失效的可能。这个办法是降低某类峰值风险，不替代容量评估、超时控制和数据库保护。

## 结合文档访问场景整理设计

简历中描述了文档访问统计的 Redis 缓存使用。公开复盘时可以讨论下面这些设计问题，而不披露真实数据：

- 缓存的是计数、列表还是完整文档？
- 哪个数据源是最终权威来源？
- 热门键的过期时间由什么需求决定？
- 缓存未命中或 Redis 不可用时，接口如何返回？
- 数据更新后，哪些键需要失效？

如果没有监控记录，不填写“减少了多少数据库查询”之类数字。可以把文章范围限定为设计说明和个人 Demo 的观察结果。

## 小结

给临时凭证设置 TTL，是在定义有效期；给业务副本设置 TTL，是在控制缓存生命周期。把这两种语义区分开，再补上失效、未命中和数据更新的处理方式，文章才会从“用了 Redis”变成可讨论的工程设计。

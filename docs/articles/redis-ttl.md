# Redis TTL 在验证码和临时状态管理中的应用

## 问题背景

验证码、短期授权状态和一次性流程标记都有生命周期。将过期策略放进存储层，可以避免依赖后台定时扫描清理所有失效数据。

## 核心原理

键应包含用途、主体标识和必要的隔离范围；值只存业务需要的信息，并设置合理 TTL。验证码验证应考虑一次性消费、重发频率、错误次数和日志安全，TTL 只是生命周期控制的一部分。

## 实现示例

写入时同时设置值与过期时间；读取后校验用途和用户，再按策略删除或更新状态。重发时先应用冷却约束，错误次数可单独计数并设过期时间。Redis 操作要避免先 SET 再单独 EXPIRE 的中断窗口，可使用原子带过期写入或 Lua。

Redis 对键维护过期信息；命令读取时会处理已过期键，后台也会主动清理一部分过期数据，因此过期数据并不保证在 TTL 刚到时立刻从内存中删除。应用需要将“已不可用”与“已物理删除”分开理解。

**示例代码或流程：**

```text
SET verify:login:user-42 123456 EX 300
TTL verify:login:user-42
GET verify:login:user-42
```

## 应用场景与边界

注册请求再经过认证服务校验验证码并处理用户注册。Redis key 应优先使用内部标识或不可逆标识，避免在监控、日志和诊断工具中暴露手机号等个人信息。`StringRedisTemplate` 示例展示的是独立的数据访问方式，具体调用应结合应用的事务和安全边界设计。

## 边界与常见问题

不要把验证码明文写入业务日志；不要把 TTL 当作防刷或授权机制的全部。验证码比较和消费要防止并发重复使用；集群环境键设计要避免泄漏敏感身份。

## 改进思路

写入值与过期时间尽量使用原子命令，验证成功后原子消费状态；重发频率与失败次数分别约束。

## 设计取舍与结论

临时状态要同时设计命名、过期、消费、重发和日志策略。Redis TTL 提供存储侧生命周期支持，不自动解决安全业务规则。

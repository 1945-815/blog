# 热门文档访问场景下的 Redis 缓存设计

## 问题背景

文档详情页可能被重复访问，缓存可以减少数据库读取，但也新增了数据同步和失效问题。是否适合缓存应结合访问频率、更新频率与数据体积判断。

## 核心原理

常见缓存旁路流程是先读缓存，未命中再查数据库并回填。缓存 key 包含文档 id 与版本或租户范围；TTL 提供最终失效边界，主动失效用于尽快反映更新。

## 实现示例

更新文档后先成功写数据库，再按约定删除缓存；读取时缓存未命中再回源。热点 key 可评估互斥回填、逻辑过期或本地短缓存，但复杂策略要结合一致性容忍度和并发量，不为 Demo 引入不必要的层次。

缓存命中直接返回序列化对象，未命中查询数据库。多个并发 miss 会同时回源；缓存失效时大量请求可能放大为数据库压力。防护方法包括限制回源并发、短暂空值缓存、随机化 TTL 和降级响应。

**示例代码或流程：**

```text
读取：GET document:{id} -> 未命中时查 MySQL -> 回填缓存
更新：提交 MySQL -> 删除对应缓存键
以上为缓存旁路示意，需另行处理并发与失败。
```

## 应用场景与边界

可以用合成文档 ID 验证缓存命中、失效和并发回源。实际效果应通过一致的请求样本与监控指标测量。

## 边界与常见问题

缓存与数据库双写有竞态；删除缓存失败要有可观测和补偿路径。不要对所有数据一律加缓存。缓存 key 需要处理权限隔离，不能因共享 key 泄漏不同用户可见内容。

## 改进思路

定义数据库更新后的失效与补偿路径；热点回源可做并发控制，缓存 key 需包含权限隔离范围。

更新路径需要定义缓存失效顺序和失败后的恢复办法。常见做法是数据库提交成功后删除缓存，并在删除失败时记录告警或通过事件补偿；如果业务允许短暂旧值，也要把可接受窗口写清楚。对高频 key，可通过请求合并减少并发回源，但锁要设置过期边界，并处理持锁进程退出的情况。空值缓存能缓解不存在数据被反复查询的问题，TTL 应较短且与权限范围隔离。

## 设计取舍与结论

缓存设计先回答缓存哪些数据、如何失效以及失败时如何回源。效果需要测量，示例文章不虚构命中率或性能指标。

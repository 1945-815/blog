# 多智能体协同的几种编排模式：路由、串联、并行与评估

## 为什么需要编排

一个模型调用可以回答单一问题；复杂任务可能要先识别意图、查询多个来源、按业务规则处理，再检查答案是否完整。把所有职责塞进一个超长提示词，会让工具权限、失败位置和输出格式都变得难以管理。

多智能体编排把任务分成可描述的角色或步骤。这里的“多个 Agent”可以是同一模型配不同提示词和工具，也可以是不同服务；名称本身不代表一定有多个独立模型进程。

## 常见模式

| 模式 | 组织方式 | 适合的任务 | 主要风险 |
| --- | --- | --- | --- |
| Router | 先判断请求类型，再交给一个专门角色 | 支持请求、账户操作或知识检索等边界较清楚的入口 | 分类错误会把请求交给错误工具；需要保留转人工或澄清路径 |
| Chain | 一个步骤的输出作为下一步骤输入 | 先抽取条件、再检索、最后整理回答 | 前一步错误会传到后续步骤，需保存中间结果并校验 |
| Parallel | 并发执行互不依赖的子任务，再汇总结果 | 多个独立文档库或服务的查询 | 总耗时受最慢子任务影响；失败、超时和重复结果需统一处理 |
| Coordinator | 中央控制器拆解任务、分派工作并汇总 | 目标开放、可能需要多轮分工的任务 | 规划可能循环或扩大范围，必须有步数、时间和工具预算 |
| Evaluator | 让检查步骤按规则审阅草稿，决定通过、修订或拒绝 | 输出需要格式、覆盖点或来源约束的任务 | 评价模型也会出错，重试会增加成本和延迟 |

这些模式可以组合。例如 Router 先选择“支持请求”或“知识库问答”，再用 Chain 完成条件抽取和检索；若有多个独立来源，可以并行查询；最终交给 Evaluator 检查是否有依据。不是每个问题都需要把五种模式串在一起。

## 从角色划分到执行流程

把推荐、购买、咨询、知识库和 coordinator 等职责拆成角色前，还需要说明每个角色接收什么输入、允许使用哪些工具、返回什么结构，以及失败后是重试、澄清还是转人工。

下面是一种说明模式关系的流程示意：

```text
用户问题
  -> Router 识别意图
  -> 推荐 / 购买 / 咨询 / 知识库角色
  -> Coordinator 汇总结果
  -> Evaluator 检查来源、范围和格式
  -> 返回回答或请求用户澄清
```

结构化查询和写入操作可由受控的 Spring AI 工具访问；文档语义召回属于 RAG。角色拆分不会自动获得数据库权限，仍应沿用 [Function Calling 的输入与权限边界](/articles/045-agent-tool-boundaries) 和 [RAG 文档问答链路](/articles/rag-document-qa)中的校验方式。

## 从设计图到实现前需要补齐的约束

1. **定义任务边界：**说明哪些请求由系统处理，哪些必须询问用户或交给人工。
2. **定义输入和输出：**每个角色使用明确 DTO 或 JSON schema，避免把整段对话原样传给所有角色。
3. **限定工具：**只把该角色当前任务所需的工具暴露给模型；写操作仍需身份校验和用户确认。
4. **控制执行预算：**限制调用轮数、并行度、总时间、token 和外部 API 次数，阻止反复规划。
5. **处理部分失败：**规定一个子任务超时或返回空结果时是否继续，并向用户说明缺失信息。
6. **保留可观察性：**为每一步记录关联 id、输入摘要、工具名、耗时和状态；不要默认记录敏感原文。
7. **验证评估器：**检查项要可观察，例如要求来源链接或指定字段齐全，不能只依赖“另一个模型觉得回答不错”。

如果工作流只有稳定的固定步骤，普通 Java 服务编排可能比自主规划更容易维护。只有当任务确实需要动态选择或组合能力时，再引入 Coordinator 等模式。

## 常见追问

### Router 和 Coordinator 有什么区别？

Router 通常负责把请求分到某个固定角色；Coordinator 会把目标拆成多个子任务、协调它们的执行并汇总结果。实际边界由流程设计决定，不能只凭类名判断。

### Parallel 一定能降低延迟吗？

只有子任务彼此独立、下游允许并发且汇总成本可控时才可能缩短等待时间。总耗时仍受最慢任务、限流和重试影响。

### Evaluator 能保证回答正确吗？

不能。它可以检查格式或是否引用给定来源，但其判断仍可能错误。高风险结论应由确定性规则、来源验证或人工流程兜底。

## 小结

多智能体的核心是编排关系，不是给普通方法换一个 Agent 名称。Router、Chain、Parallel、Coordinator 和 Evaluator 分别解决不同类型的流程问题；每多一个步骤，也多一处成本、延迟和失败边界。

# 后端接口协作：契约、联调与问题定位

接口交付涉及的不只是 Controller。字段约定、认证授权、数据写入、异常映射和客户端行为共同决定一个接口是否可用。排查问题时，先把客户端观察与服务端事实对齐，再沿请求链路定位。

## 先固定接口契约

对每个接口记录方法与路径、请求字段及约束、身份要求、成功响应、错误状态和副作用。DTO 与校验注解表达输入边界；响应 DTO 则控制字段暴露，避免把持久化实体直接当成稳定的 API 契约。

变更契约时要考虑已有调用方。字段新增通常可以保持兼容；删除或改变字段含义、状态码、分页顺序时，需要评估客户端升级路径。接口文档应从实现或同一份契约生成，并纳入变更审查。

## 沿请求路径排查

```text
客户端请求
  -> 网关与认证
  -> 路由、参数绑定和校验
  -> 业务服务与数据访问
  -> 响应映射
```

先确认请求方法、URL、请求头和脱敏后的请求体，再检查服务端收到的参数、认证主体、SQL 条件与数据库结果。网关可能改写路径或转发头；参数绑定错误也可能发生在 Controller 方法执行之前。只看页面提示，通常不足以判断失败发生在哪一层。

## 留下可复现证据

问题记录至少包括复现步骤、期望与实际结果、请求标识、相关日志片段、受影响的状态以及修复后的验证方式。日志中应屏蔽口令、令牌、手机号和业务正文；请求标识用于关联网关与服务日志，但不应包含个人数据。

Code Review 可以围绕权限范围、空值和边界输入、事务及并发条件、SQL 选择性、错误响应稳定性和兼容性展开。修复后除验证成功路径，也要覆盖无权限、重复请求、记录不存在和下游超时等相关失败路径。

## 设计取舍

接口契约越明确，联调时越容易分清客户端输入错误、服务端逻辑错误和环境问题。但并非所有内部细节都应返回客户端：外部响应给出稳定错误码和可理解提示，内部日志保留足够的诊断上下文，同时避免敏感字段。

分析具体技术场景时，应围绕可公开复现的接口契约、请求链路和脱敏证据展开。

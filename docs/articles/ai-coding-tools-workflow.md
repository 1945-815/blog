# Codex 和 Cursor 如何辅助接口开发与代码理解

### 文章定位

本文基于路线图主题展开。实习项目相关叙述严格限定在简历已列出的职责；无法确认的工程细节使用通用示例说明，不冒充生产实现。

### 学习目标

- 理解业务问题与技术组件的对应关系。
- 能画出关键模块或状态流转，并解释失败边界。
- 能区分团队成果、本人负责内容与个人练习。

## 一、为什么学习这个技术

AI 编程工具可以协助搜索调用链、生成样板代码和解释报错，但项目上下文不完整时也会给出错误假设。工具输出应作为待审阅的改动建议。

## 二、技术原理

先给出目标、范围、约束和验收条件；再要求工具定位相关文件并解释依赖；需要改代码时限制文件范围、保持小 diff；最后由开发者核对业务语义、权限、异常和测试结果。

## 三、核心代码实现

一个接口开发流程可以是：阅读现有 Controller/Service/Mapper 模式；让工具列出待改文件与方案；检查生成 diff；运行项目已有验证命令；手工审阅 SQL、权限检查、日志和 API 兼容性；将工具辅助和本人决策分开记录。

代码助手可能结合当前上下文、检索到的文件和用户指令生成补丁；上下文遗漏会造成幻觉式引用或风格偏差。对话中的文件和生成结果不等于编译通过，也不等于业务正确。

### 源码与机制观察

记录一个真实、脱敏的任务：输入提示词、工具定位的文件、实际修改、人工发现的问题和最终验证证据。只写本人实际使用过的工具与步骤；不把工具替代审查或测试。

## 四、真实项目落地

简历确认实习中使用 Cursor 辅助分析与接口开发；Codex 的示例用于个人代码理解练习。两类工具的输出都需本人检查。

## 五、遇到的问题

不要粘贴客户资料、访问令牌或未授权源代码。不要盲目接受跨目录重构。对 AI 生成代码运行必要的现有检查，并复核依赖许可证、SQL 参数化和权限边界。

```text
任务：为文档列表增加分类筛选和分页
约束：遵循现有 DTO / Service / Mapper 风格；只修改相关文件
验收：空条件可用、页码受限、排序字段白名单化，并说明验证命令
```

## 六、优化方案

把任务拆成小范围修改，先看差异再做验证；人工复核权限、SQL、异常和项目约定。

## 七、个人思考

AI 工具可减少重复搜索和样板工作，但正确性责任仍由开发者承担。小任务、清晰 diff 和可复现验证更适合团队协作。

## 延伸：面试问答

### 怎样让工具更少猜测？

提供目标文件、现有约定、输入输出、禁止改动范围和验收条件，并要求它先说明假设。

### 工具生成代码后先看什么？

先看改动范围和差异，再查权限、校验、SQL、异常处理及与调用方的兼容性。

### 能把 AI 使用写成个人贡献吗？

可以如实说明使用场景和人工复核过程，成果归属仍以本人完成和理解的工作为准。

## 延伸：项目追问

**追问：**怎样在面试中说明该设计和个人职责？

**回答思路：**从实际参与范围开始，说明问题、关键实现和验证方式；示例代码用于解释机制，不暗示它就是公司的原始代码。对没有实际测量的数据不提供指标。

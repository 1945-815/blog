# 审批状态、任务状态与业务状态如何对应

## 问题背景

同一条记录可能同时有关联流程实例、当前待办任务和业务对象状态。如果接口只返回一个“状态”，使用者很难判断它代表审批是否结束、当前是否有人处理，还是业务是否已经履约。

## 核心原理

- **流程实例状态**：流程引擎视角，例如运行中、已完成或已挂起。
- **任务状态**：某个用户任务是否待领取、处理中或已完成。
- **业务状态**：领域对象当前阶段，例如待确认、已确认、已取消。

三个状态由不同组件维护，但会通过业务 id、流程实例 id 和任务 id 关联。流程任务完成不必然意味着业务已完成，例如审批通过后业务对象可能仍处于待执行阶段。

## 实现示例

先列出业务动作、操作者、前置状态和结果状态，再定义允许迁移。比如预约可以从待确认进入已确认或已取消；完成审批后由业务服务根据审批结果推进业务状态。接口可同时返回业务状态和待办摘要，避免让客户端猜测。

状态更新应通过业务服务入口进行，不能让任意 Controller 直接写状态字段。对于并发更新，可使用版本号或以旧状态作为 SQL 条件；检查受影响行数，未更新时重新读取状态并返回业务冲突。

```sql
UPDATE appointment
SET status = 'CONFIRMED', version = version + 1
WHERE id = ? AND status = 'PENDING' AND version = ?;
```

## 应用场景与边界

结合审批与预约类场景，分别梳理流程状态、任务状态和业务状态的转移。具体节点应依据对应的业务规则定义。

## 边界与常见问题

不要把流程引擎的内部状态码直接暴露为业务 API；不要让流程变量成为唯一业务数据来源。状态迁移应记录操作者、动作和时间。流程失败或重复回调时，需要查询关联 id 并提供对账和修复方式。

## 改进思路

状态迁移集中在领域服务，更新时再次验证旧状态；流程异常应保留关联 id 以便追踪和修复。

## 设计取舍与结论

状态模型应说明责任主体、合法迁移和并发规则。Activiti 可以管理任务流转，业务服务仍负责领域状态、权限校验和审计。

# 预约与审批的状态建模：业务状态、任务状态与幂等

预约和审批经常出现在同一条业务链路中，但它们代表不同事实。预约描述资源时段是否被占用以及服务进度；审批任务描述谁需要在何时处理什么决定。把两者合并成一个状态字段，会让并发更新、重试和审计都难以解释。

## 拆分业务对象

一个通用的资源预约流程至少涉及预约记录、可预约资源或时段，以及可选的审批任务。预约记录保存用户、时段和业务状态；审批引擎保存流程实例、当前任务和处理意见。二者通过稳定的业务主键关联，不能只靠任务名称或列表顺序定位业务记录。

例如，预约可采用 `PENDING`、`CONFIRMED`、`CANCELLED`、`COMPLETED` 等状态；审批任务则由流程引擎管理。审批通过后，业务服务仍需检查预约当前状态和资源可用性，再决定是否确认预约。流程任务完成与业务操作成功不是同一件事。

## 约束状态转换

状态转换应有明确前置条件。数据库条件更新可以避免并发请求覆盖彼此的决定：

```sql
UPDATE appointment
SET status = 'CONFIRMED', version = version + 1
WHERE id = ? AND status = 'PENDING' AND version = ?;
```

只有影响行数为 1 时，调用方才能继续处理成功路径。时段唯一性可以用合适的唯一约束或锁定方案保护；在事务中先查询、再写入，并不能单独消除并发下的重复预约。

创建类请求可接受幂等键，并在数据库中对调用方范围和幂等键建立唯一约束。重复请求返回第一次处理的结果或明确的冲突响应。短信、邮件等外部副作用不能由数据库事务回滚；需要可靠通知时，可采用 Outbox 等模式另行处理。

## 审批与业务更新的边界

审批接口应校验操作者是否有权处理当前任务、任务是否仍可处理，以及业务记录是否仍处于允许状态。常见流程是先在同一业务边界内核对任务和预约，再推进流程并更新业务状态；具体事务能力取决于流程引擎、数据源和调用方式，不能假设跨服务调用天然原子。

保留操作者、决定、意见、发生时间和关联业务 ID 等审计信息。意见和用户输入需要长度限制与输出转义；敏感字段应最小化保存并配置适当的访问控制。

## 验证边界

至少检查重复提交、同一时段并发创建、审批任务被重复完成、审批通过时预约已取消、下游通知失败和流程重试等情形。Redis 可用于短期状态或加速读取，但关键预约事实和唯一性约束应由持久化层保护。

为突出状态边界，示例只保留预约记录、资源时段和流程任务三类数据；具体实现应按实际状态规则补充字段与约束。

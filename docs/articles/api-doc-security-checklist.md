# Java 后端项目中的接口文档与安全检查清单

## 问题背景

接口不仅是 Controller 方法，还包括请求结构、响应语义、权限要求和失败行为。文档落后于代码会给前端联调和后续维护带来额外成本。

## 核心原理

契约要说明路径、方法、字段类型与约束、身份要求、分页和错误响应。安全评审要从认证、授权、输入、数据范围、秘密和日志多个维度检查，不能只依赖单一注解。

## 实现示例

为一个列表接口记录查询参数、最大页大小、排序白名单和权限规则；对创建与更新接口描述幂等或重复提交语义；给出一份不含敏感值的请求响应样例。每次接口变更同步更新文档并在联调前核对。

文档工具通常从注解或接口定义生成模型，但无法完整推断业务权限和状态规则。CI 可加入契约生成或格式检查，安全敏感接口仍需人工审查和授权测试。

### 接口评审检查项

- 请求字段是否有类型、长度、范围和必填约束？
- 写操作是否校验当前状态、重复请求和数据归属？
- 列表接口是否限制分页大小并过滤当前用户无权查看的记录？
- 错误响应是否稳定，服务端日志是否包含 request id 且避开秘密？
- 文档示例能否用合成数据重放，并与当前接口版本对应？

这些检查不能替代专项安全测试，但能把常见遗漏前移到代码评审阶段。对于权限敏感接口，至少准备一个无权访问的负向用例。

**示例代码或流程：**

```text
GET /documents?page=1&size=20
200：只返回当前用户有权查看的文档
400：页码或排序参数非法
401：未认证；403：已认证但无权访问
```

## 请求签名、防重放与限流边界

接口安全应按威胁建模，不应把客户端摘要、时间戳或限流阈值误认为完整防护：

| 控制项 | 可采用的机制 | 需要验证的边界 |
| --- | --- | --- |
| 限流 | 按用户、令牌或可信来源设置有界速率；Redis 固定窗口可用原子操作更新计数 | 代理后的客户端地址必须来自可信代理；固定窗口可能在窗口边界出现突发 |
| 请求完整性 | 服务端持有密钥的客户端或服务间请求可用 HMAC-SHA-256 对规范化内容签名 | 浏览器代码中的固定密钥可被提取；MD5 或公开“盐”不能用于身份认证 |
| 时间有效性 | 校验时间戳位于服务器允许的前后时间窗 | 时间窗只能限制请求新鲜度，不能阻止窗口内重复提交 |
| 重放防护 | 对 nonce 或事件 ID 执行带 TTL 的原子去重 | 去重状态需覆盖允许的重试窗口；业务幂等键仍需单独处理业务副作用 |
| 传输保密 | 使用 HTTPS 保护传输链路 | HTTPS 不替代身份认证、授权和敏感数据最小化 |

签名校验应默认拒绝缺少签名或校验失败的请求。调试开关若确有需要，应隔离在不可访问生产环境的配置中，并在发布检查中确认关闭。

### 面向真实接口的安全边界

浏览器客户端无法保守长期共享密钥，因此不要把固定 MD5 盐或 HMAC 密钥写进 JavaScript 并称为防伪。先用 HTTPS、身份认证、逐接口授权、服务端限流和输入校验建立基本边界。服务到服务或 webhook 等确实能安全配置密钥的场景，可用 HMAC-SHA-256 对明确的请求方法、路径、主体摘要、时间戳和事件 ID 做签名；服务端验证签名后，再用短 TTL 的一次性 nonce/事件 ID 去重。nonce 校验需要原子写入，重复值拒绝；业务幂等键解决重复提交的业务效果，两者目的不同。

客户端时间必须限制在服务器允许的前后窗口内，例如检查 `serverTime - window <= clientTime <= serverTime + window`，而不是只检查一个方向。时间窗负责拒绝过旧或过新的请求，一次性 nonce 才负责拒绝窗口内的重放。外部请求签名不能替代权限检查，也不能替代 HTTPS。

## 边界与常见问题

文档样例不要包含真实手机号、token 或内部地址；避免“成功”响应掩盖部分失败；权限需要验证资源归属，不能只校验是否登录。日志中使用必要上下文而非完整敏感请求。

## 改进思路

把字段约束、失败码、数据范围和负向权限用例纳入评审；接口变更与文档更新在同一次提交中核对。

## 设计取舍与结论

接口文档和安全检查是团队契约的一部分。用明确字段和负向用例验证，能减少联调中的隐式假设。

# RAG 文档切分与向量检索：实现和评估边界

## 问题背景

整份长文档直接作为一个向量，难以对应用户提出的局部问题；切得过碎又可能丢失上下文。分块和检索是 RAG 应用质量的重要变量。

## 核心原理

Chunk 是检索单元，Embedding 把文本映射到向量空间，向量检索按相似度召回候选。块长度、重叠、标题层级和元数据共同决定可检索信息边界。向量相似不等于答案正确，需要检索后检查原文。

## 实现示例

准备公开小文档；按段落和标题切分，保存 source、chunk id、标题和页码；调用选定的 Embedding 接口生成向量；写入向量存储；以具体问题执行 top-k 查询。逐项查看候选文本，而不只看相似度分值。

离线阶段进行解析、切分、嵌入和索引；在线阶段对 query 做同模型嵌入并做近邻搜索。更换模型或距离度量可能要求重建索引。混合检索可结合关键词和向量，但融合排序参数需要基于样例验证。

### 源码与机制观察

为每个查询记录 query、候选 chunk、分数、过滤条件和人工相关性判断。比较不同切分尺寸时只改变一个变量并固定样本文档，记录观察结果，不把小样本主观判断包装成准确率。

## 应用场景与边界

以公开短文档验证切分与向量召回，保留标题和来源元信息；本文聚焦检索链路，不涉及模型训练或特定编排框架。

## 边界与常见问题

不要将分块长度只按字符数机械切割；保留标题和段落边界。Embedding 维度、模型版本和索引配置需要一致。权限元数据必须参与过滤，不能只在最终提示词中提醒模型保密。

```text
Chunk {
  id: "doc-12#p3-c2",
  text: "段落正文……",
  metadata: { source: "guide.md", heading: "部署", page: 3 }
}
```

## 改进思路

固定样本文档，只改变一种切分参数比较召回；保留模型版本和来源元数据，避免用小样本宣称准确率。

## 设计取舍与结论

小型 RAG Demo 的价值在于能观察从文档到召回的完整链路。记录样本、配置与局限，才有可复现的结论。

## 常见问题

### 块越小检索越准吗？

不一定；太小可能丢失语义上下文，太大则降低局部定位能力，需按文档结构和问题类型验证。

### Embedding 模型更新后能复用旧向量吗？

向量空间可能变化，通常应将模型标识写入索引元数据，并评估是否重嵌入和重建索引。

### top-k 越大越好吗？

候选越多会增加噪声和上下文成本，应该结合召回观察和生成窗口选择。

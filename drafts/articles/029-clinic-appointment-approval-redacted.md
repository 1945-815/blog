# 诊所预约与审批平台的业务流程设计（脱敏）

## 背景与问题

简历中描述了面向个人经营诊所日常运营的后端项目，涉及患者预约、诊疗服务项目、服务订单和内部审批。本文仅使用简历列明的范围，不包含任何真实患者信息或机构细节。

## 核心概念与设计

预约、服务项目和订单是不同业务对象；预约关注时段与确认，订单关注服务项及履约状态，审批任务描述内部审核。Spring Boot、Spring Security、MyBatis、MySQL、Redis、JWT 和 Activiti 7 分别承担接口、认证、持久化、临时状态和流程编排等角色。

## 实现与运行机制

可以先定义患者预约创建、取消和查询；再维护诊疗服务项目的新增、修改、上下架和分页查询；服务订单按预约信息创建并有明确状态；内部审批通过 Activiti 定义节点和候选处理人。简历还提到预约规则校验、重复提交校验与事务处理。

一次预约请求经过身份验证、参数校验、业务规则检查与数据库写入。关键唯一性条件由数据库约束参与保护；审批接口校验当前任务和业务状态后推动流程。Redis 可用于验证码或临时状态，不能作为预约事实的唯一存储。

## 机制与代码观察

从预约实体、服务订单实体和流程定义之间的关联关系理解模型；检查 mapper 查询条件、状态更新 SQL、唯一约束和 Activiti 任务查询。具体字段与节点名称应使用合成数据的个人 Demo 演示。

## 问题与优化

医疗业务数据高度敏感，不能上传真实患者信息、预约记录或诊所截图。不要把预约状态和审批状态混成一列；不要声称简历未提供的并发规模、上线情况或效率指标。

```text
预约：待确认 -> 已确认 -> 已完成
   |             |-> 已取消
   |-> 已取消
审批：待审批 -> 通过 / 驳回
```

## 高频面试问题

### 预约和服务订单要分表吗？

取决于领域属性和生命周期；当预约时段与订单履约存在不同操作和状态时，分开建模通常更清晰。

### 审批结果如何影响业务？

审批任务完成后由业务服务校验并更新对应业务状态，且保留操作者、意见和时间等审计信息。

### Redis 是否能保证不重复预约？

仅凭缓存检查难以处理所有并发边界；关键唯一性应由数据库约束或可靠的并发控制保护。

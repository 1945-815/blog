# 预约和服务订单中的状态流转与重复提交

## 背景与问题

预约创建可能遇到用户连点、网络重试和并发抢占。将预约与服务订单状态混为一列，会让操作规则难以验证。

## 核心概念与设计

分别定义预约状态和订单状态，并为每个状态列出允许动作、操作者与副作用。后端按当前状态进行条件迁移；唯一约束或幂等键处理重复请求，事务覆盖同一数据库中的关键写入。

## 实现与运行机制

画出预约创建、确认、取消和履约的状态图，明确终态和是否允许重开。创建时使用业务唯一键约束同一用户对同一时段的重复预约；服务层返回已存在记录或冲突响应，不能静默创建第二笔。

并发请求的状态读取可能同时成功，因此最终写入需由条件更新、唯一索引或锁保护。事务保证相关表操作原子提交；外部通知放在事务提交后通过消息或待发送记录处理。

## 问题与优化

不要用前端按钮禁用承担幂等责任；不要允许任意状态回退。数据库冲突需要映射为业务响应。删除或取消要保留必要审计，而不是覆盖历史事实。

## 面试总结

### 状态机能解决重复提交吗？

状态机表达合法迁移；重复创建仍需业务唯一键、幂等键或并发控制。

### 取消后能否再次预约？

由业务规则决定，可通过新的预约记录表示再次意图，不应含糊复用已终止记录。

### 事务能覆盖短信通知吗？

普通数据库事务不能回滚外部通知，应采用提交后异步发送并设计重试或补偿。

## 条件更新示例

状态迁移可以在 SQL 条件中再次验证旧状态，只有匹配时才更新一行。服务层检查受影响行数：为零时重新读取当前状态并返回冲突，而不是无条件覆盖。

```sql
UPDATE appointment
SET status = 'CONFIRMED', version = version + 1
WHERE id = ? AND status = 'PENDING' AND version = ?;
```

该写法适合说明乐观并发控制；具体列名和状态值需按实际模型调整。若还要创建订单或发送事件，必须明确事务与提交后动作的边界。

## 总结

状态模型定义合法业务过程，唯一约束和幂等机制保障并发写入。两者配合比单靠事务或界面限制更稳健。
